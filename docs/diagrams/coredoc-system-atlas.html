01 · The big picture

Three data planes, one grounded agent

Coredoc maintains three connected views of your engineering organization: the code graph (what the system is), the intent overlay (what it should do), and the delivery spine (how work actually flows). Agents get all three as grounded context through MCP; the team gets delivery dashboards. Everything else on this page is a zoom into one of these planes.

02 · Where it runs

Local, cloud — or entirely inside your infrastructure

Three deployment modes, three trust postures. Local: the CLI, MCP server and graph file live on the developer's machine — code never leaves it. Coredoc cloud: a managed workspace for teams (Postgres control plane, Ladybug graph snapshots on R2). On-prem: the same server image runs inside the client's own network against a client-owned Neo4j graph and S3-compatible storage — Coredoc has no access whatsoever: no code, no data, no logs ever cross the boundary, because the network path simply does not exist.

03 · Code graph

Extraction: author once, parse forever

Instead of a bespoke parser per repo, Claude authors a ~50-line declarative profile describing the repo's conventions. A deterministic engine (tree-sitter + SCIP) applies it to every matching site — exhaustive recall, precision by construction, with a scorecard loop gating coverage at ≥80%. The result is local-first: code never leaves the machine unless a team opts into a shared workspace — Coredoc-hosted SaaS or the client's own on-prem deployment — and a GitHub Action keeps the shared graph fresh on every merge.

04 · Engineering workflows

Spec-driven development with built-in telemetry

The coredoc-workflows plugin routes every task by intent, risk and scale. Large changes flow through spec → plan review (a human gate) → implement → review, all anchored to a single spec.md artifact with use cases, business rules and acceptance criteria. In parallel, session hooks and native OTel logs stream through a local sanitizing relay — structural events only, never code or prompts — to a workspace endpoint that can itself be self-hosted on-prem.

05 · Intent layer — to be

Reviewed product truth beside the code graph

Today agents reconstruct product behavior from tickets, specs and code on every task. The intent layer makes it durable: an agent skill captures candidates from finalized specs (later: bootstrap mining of Jira, ADRs and the code graph itself), a maintainer explicitly accepts or rejects them in a git-tracked file, and code anchors track freshness against the graph. Agents consume it through one bounded read-only MCP tool — routed IDs are reused between workflow stages, so context stays cheap.

06 · Delivery analytics

Jira, Git and agent sessions on one spine

Hourly connectors poll Jira and GitHub; agent sessions report tokens, cost and tool usage over OTLP; workflow skills emit run and stage events. Everything is normalized and fused — by task identity and actor identity — into one canonical delivery spine. That's what powers the answers a lead actually asks: what happened on this task end to end, what did it cost, what shipped, and where rework is coming from. The server runs in Coredoc cloud or on-prem — in the latter case all telemetry stays inside the client's network.

07 · Target SDLC

One spec from PRD to merge — and back into context

The planned end state: product writes a PRD with Coredoc MCP context, dev turns it into a spec and implementation with the workflow skills, QA validates acceptance criteria with a browser-use agent, and CI reviews the PR against the spec. On merge, CI re-extracts the code graph and intent overlay — so the next PRD starts from fresh, grounded context. The loop closes.
